### T-FAB-01 — Замовні тканини

#### Перводжерело (Вадим)

Канон: [§1 — Замовні тканини](./references/vadim/stosovno-zmin-u-bazi.md#1-замовні-тканини) (лист Вадима).

#### 1. Замовні тканини

Має бути 8 замовних тканин.

Нові назви:

- Замовна тканина 1к до 3$
- Замовна тканина 2к до 4$
- Замовна тканина 3к до 5$
- Замовна тканина 4к до 5$
- ...

- Уточнити ще 4 назви, яких немає в цьому списку.
- Додати ці атрибути до всіх диванів і чохлів, щоб Odoo створив відповідні варіанти товарів. Також додати їх до специфікацій цих товарів.

#### Робота в Matrix

**Чому 4 з 8, не помилка Вадима.** У §1 явно **4 рядки + «…» + «уточнити ще 4 назви»** — решта списку від **замовника**. До повних **8** точних назв Odoo **не** чіпаємо.

**«Перемножуються».** Атрибут «Тканина» = **один** вибір на диван (як Рене/Грегор). Нові значення на шаблонах з іншими опціями **множать варіанти (SKU)**, а не «складати 1к+2к» і не кілька замовних в одному замовленні. Вадим про multiply мав рацію; **ціна/extra** — окремо (T-PRC-01).

**«1к», «до 3$», «до3$».** Канону в репо немає: ймовірно **tier 1–4** + **стеля USD** (метр / закупівля / доплата — **уточнити у клієнта**). «до3$» разом — **швидше друк**, не окремий термін.

**Блокери.** Замовник — 8 назв + відповіді на «к»/ціну/одна тканина/всі дивани+чохли/ліжка. Колега — чи ліжка в тій самій матриці 8. **Чернетка** запиту — **не** слати до відповіді **T-VOL-01** (відправиш сам).

**Після клієнта.** Зафіксувати 8 назв тут → `npm run add-fabric` (batch) → BOM; extra узгодити з T-PRC-01.

### T-DESC-01 — Опис рядка замовлення в цеху

#### Перводжерело (клієнт, не Вадим)

Немає в листі Вадима «Стосовно змін у базі даних».

Питання клієнта: «І ще питання, можливо зробити, коли додати опис, щоб воно в інших процесах відображалось?»

Контекст: Продажі → рядок замовлення під назвою товару (наприклад «Диван Доррі-3 Механізм») → поле **«Введіть опис»**. Менеджер пише індивідуальні характеристики / примітки до цього виробу. Потрібно, щоб майстер бачив той самий текст на виробничому замовленні, на робочому місці / цеху, у маршрутному листі і на перевірці якості.

#### Робота в Matrix

**Блокери.** —

**Залежність (не блокер).** Той самий ланцюг, що T-QAL-02: `sale.order.line` → MO (`mrp.production`) → WO (`mrp.workorder`) → `quality.check`. Уже є `x_studio_x_so_line_uid` (`S00… / № 01`).

**Статус 2026-11-09 — зроблено в картках.** Related `x_studio_so_line_note` без Python. Studio loc **93/100**. Поля **25253/25258/25260**, views **3846–3849**. Скрипт `studioSoLineNote.ts`. Лист клієнту: [`T-DESC-01-povidomlennya-kliyentu.md`](../../furniture/reference/T-DESC-01-povidomlennya-kliyentu.md). **Чекаємо відповідь** які ще екрани/PDF зі списку (відправлено 2026-11-09). Не блокер інших задач.

**Суть.** Поле «Введіть опис» = стандартне `sale.order.line.name` (Опис рядка), не окремий атрибут товару. Odoo **не** копіює його на MO / WO / якість сам. Не писати цей текст у шаблон товару чи BOM — тоді він стане спільним для всіх замовлень.

Канон мапінгу (MTO, як зараз дивани):

1. Джерело: `sale.order.line.name` (або окреме Studio-поле `x_studio_line_note`, якщо `name` має лишатися чистою назвою для PDF рахунку).
2. Зв’язок з MO: `stock.move.sale_line_id` і/або `mrp.production` через `procurement_group` / `origin` + уже наявний `x_studio_x_so_line_uid`. У Odoo 19 перевірити, чи є `mrp.production.sale_line_id` (модуль sale_mrp).
3. Studio related Text на `mrp.production` (наприклад `x_studio_so_line_note`) → related `sale_line_id.name`.
4. Те саме related на `mrp.workorder` через `production_id` (форма WO + Shop Floor / планшет цеху).
5. Те саме related на `quality.check` через `production_id` (список «Перевірки в процесі» — поруч з T-QAL-02).
6. Маршрутний лист / PDF MO: додати поле в звіт Studio (форма без друку цех не бачить).
7. Працює лише якщо MO народжується з рядка SO (MTO). Складське MO без рядка продажу — опису немає.

Автоматизація (запасний шлях, як авто-SN): on create MO скопіювати `sale_line_id.name` у stored Text — тоді текст не зламається, якщо рядок SO пізніше змінять. Related завжди живий.

#### 7. Зміна типу операцій для ламінату та накладок

Ламінат і накладки мають обліковуватися як закуповувані товари, а не як продукція власного виробництва. Тому замовлення на виробництво для них більше не потрібні.

Причина: клієнт використовує іншу програму для нарахування зарплати за об'ємом і кресленнями. Тому клієнт хоче, щоб ці розміри поповнювалися за принципом [Боннель] — з усіма доступними розмірами.

Уточнення щодо товарів:

- 🧩 [Ламінат — нарізані деталі]
- 🧩 [Ламінат кольоровий — лист]
- 🧩 [Ламінат — лист]
- 🪤 [Накладка]

Для цих товарів необхідно:

- У маршрутах прибрати операцію «Поповнити замовлення (ВНЗ)».
- Увімкнути прапорець «Купівля».
